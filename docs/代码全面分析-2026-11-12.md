## 一、前端上传引擎层 `src/components/ZustandFileUpload/`

**健康度：高成熟度，最大短板是「同一文件的并发任务互斥」未约束。**

### P1

#### 1. Worker 池以 `fileId` 单键复用 → 并发双发致 worker 孤儿/误杀 ✅ 已修复（2026-11-12）
- 位置：`services/uploadWorkerBridge.ts:133-163, 245, 255-276, 397`
- 根因：`taskWorkerMap`/`taskSettleMap` 均只保留「最新一次」worker。同一文件被并发发起两段 `runUploadTask` 时，第二次 `set` 覆盖第一次映射：
  - `cancelUploadTask(fileId)` 只能定位到后一个 worker，前一个变孤儿（继续空跑上传）；
  - 前一个的 `abort` 触发 `handleAbort` 执行 `taskWorkerMap.delete(fileId)` 并 `disposeUploadWorker`——**终止了另一批次正在使用的 worker**，其 `runUploadTask` 的 Promise 只能靠 120s 空闲看门狗兜底，期间该文件显示「上传中」却假死。
- 触发入口：见下方 P1 #2。
- 修复：将两 Map 的键改为「fileId + 任务实例标识（自增 taskId）」，`cancelUploadTask` 按实例精确取消；或在 `runUploadTask` 入口对同一 fileId 做互斥。

#### 2. `retryUploadFile` 绕过批次编排 ✅ 已修复（2026-11-12）
- 位置：`hooks/useBatchUploaderController.ts:678-726`（vs 批次 `processFileUpload` `:139-298`）
- 根因：直接调用 `processFileUpload(draft)`，**不设 `isUploading`、不绑 `activeUploadAbortRef`、不登记 `cancelledInBatchIdsRef`/`userCancelledIdsRef`**。
  - 与「上传全部」并发即触发 P1 #1 的 worker 复竞态；
  - 该次重试无法被整批取消中止，只能等 30s 单请求超时或 120s 看门狗；
  - `catch` 还吞掉异常只返回 `{success:false}`。
- 修复：改为走 `runBatch`（与 `resumeUploadFile` 一致），复用 `beginBatchSession`/`setIsUploading`/信号与取消集合。

### P2

- **连接级错误零重试 + 线性退避**（`worker/fetchWithRetry.ts:217-235,243-269`；`worker/chunkPipeline.ts:198-204,253-261`；`worker/errorClassification.ts:19-28`）：分片遇 `Failed to fetch`/超时直接 `reject` 不重试，仅 5xx 走 `maxRetries`；退避为线性（`retryInterval*currentAttempt`）无指数无抖动。弱网下一次闪断即放大成整文件失败，与用户 `maxRetries` 预期不符。修复：对连接级错误施加有限重试（复用 `maxRetries` 与退避），区分「单分片耗尽」与「整文件后端不可用」。

## 三、后端服务层 `server/src/`

**健康度：安全底座扎实（路径穿越/符号链接/SQLi/鉴权 fail-closed/错误脱敏/限流代理就绪/崩溃续传均过关）；本轮仅发现 P2 级「已修复清单周边的相邻缺陷」。**

### P2

- **合并「源分片清理」早于「事务提交」**（`controllers/uploadController.js:636-639` 早于 `:646-686`）：moveIntoPlace 成功后先 `unlink` 全部源片，再开事务写库。若 DB 事务（upsert/update/commit）失败 → catch 回滚并删 `targetPath`，源片已删、DB 回滚到 `status:1`；下次 `/merge` 报 400「分片不存在」，被迫全量重传。修复：源片删除移到 `commit()` 成功之后。
- **`instantCheck` 重置分支未保护正在合并的文件**（`uploadController.js:149-162` vs `:259`）：abortUpload 有 `getMergingStorageIds().has(storageId)` 的 409 保护，但 `instantCheck` 在 chunkKey 的 size/chunkSize 变更时直接 `resetChunkResults`（flush+unlink+status:0），会清掉在飞合并的源片 → 合并不对称失败。修复：重置分支同样先判 409 或纳入合并锁。
- **全局单把 `"upload-quota"` 锁 + SQLite 单连接**（`uploadController.js:324` + `config/database.js:19-24`）：所有用户/文件的分片上传、写盘、flush 被同一把常量锁串行化，整条写路径并发度为 1；慢磁盘或 `SQLITE_BUSY` 重试会阻塞全站上传。修复：锁键改 `quota:${userId}:${storageId}`，仅同用户同文件串行。
- **合并只清理 `0..total-1` 分片**（`uploadController.js:636-639,676-684`）：`FileChunk.update status:2` 无 `chunk_index` 过滤，会把 `file_id` 下**所有** `status:1` 分片（含 index ≥ total 的孤儿）置 2；但磁盘清理只遍历 `0..total-1`，index ≥ total 的分片文件残留等 janitor TTL。修复：合并成功后按实际 chunk 集合或 `file_id` 全量清磁盘。
- **崩溃窗口遗留 uploads 孤儿文件**（`uploadController.js:629→686` 之间 SIGKILL）：moveIntoPlace 成功、File 行未提交时被强杀，`UPLOADS_DIR` 多出无 DB 记录文件；janitor 只扫 `tmp/upload` 不扫 `uploads`，亦无启动期对账。修复：bootstrap 增加 uploads↔DB 对账（按 `File.file_path` 反查 `storedFileName` 删无主），或显式文档化该窗口。
- **`replacedCounted` 竞态**（`uploadController.js:304-309` vs `:369-376`）：`existingDbChunk` 在锁内先于 `getUserChunkUsage` 读取；合并走独立 `mergeLocks` 不与 `upload-quota` 互斥，可能在两次读取间把分片置 `status:2`，导致配额轻微误拒/少计。修复：同事务/一致性快照内读取，或改以 DB 实际行反推 replaced。
- **Cookie 鉴权 SameSite/CSRF 纵深**（`app.js:73-77` + `middleware/auth.js:93-108`）：服务端只读取 `FILE_AUTH_COOKIE`，`SameSite`/`HttpOnly` 由签发方决定；配合 `CORS_ORIGIN=*` 反射任意 Origin 存在理论面。修复：部署基线要求签发方设 `SameSite=Lax`+`HttpOnly`；`CORS_ORIGIN=*` 场景明确禁止携带凭据。

### 最该补的 3 个测试
1. **合并提交前崩溃孤儿回收**：扩展 `t73-crash-recovery.test.js`，在 moveIntoPlace 成功后、commit 前 SIGKILL，断言重启后 `UPLOADS_DIR` 不残留无 DB 记录文件（或 bootstrap 对账能清），客户端可正常重合并。
2. **合并与上传/instant 重置同文件并发互斥**：构造「`/merge` 进行中 + 并发 `/upload` 同 index 覆盖 + `/instant` 触发 resetChunkResults」，断言合并不被「分片不存在/MD5 不一致」打断，且重置路径对正在合并的文件返回 409。
3. **合并声明范围外多余分片清理**：先传 index 0..49 与 index 100，再 `total=50` 调 `/merge`，断言 index=100 分片文件被同步清理、磁盘与 DB 一致。

### P1

#### 1. CI 失败定位循环漏 `summarize:skips` ✅ 已修复（2026-11-12）
