## 三、场景明细（通过项）

### S01 单文件上传

**步骤**
1. 打开 `http://localhost:5173/`
2. 选择 `sample-1kb.txt`
3. 点击「开始上传」
4. 观察状态，核对网络请求与磁盘落盘

**预期**：走完 `instant → status → upload → merge` 全链路，状态变为「已完成 100%」，服务端落盘 873 B。

**实际**
- 状态由「准备中」→「上传中」→「已完成 100%」。
- 网络面板请求序列（全部 200）：

| 请求 | 结果 |
|---|---|
| `POST /api/file/instant` | 200，`uploaded:false` |
| `GET /api/file/status` | 200，`chunks:[]` |
| `POST /api/file/upload`（chunk 0） | 200 |
| `POST /api/file/merge` | 200 |

- 服务端 `server/uploads` 出现 873 B 文件，大小与源文件一致。

**结论**：✅ 通过

### S02 多文件批量上传

**步骤**
1. 一次性多选 `sample-1kb.txt` + `sample-2mb.csv` + `big-12mb.bin`
2. 点击「开始上传」
3. 观察三条记录的各自状态与批量栏文案

**预期**：3 个文件全部完成；小文件可秒传；大文件按片上传；批量栏汇总成功/失败数。

**实际**
- 三条记录最终均为终态：`sample-1kb.txt` 显示「秒传成功」，`sample-2mb.csv`（2 片）与 `big-12mb.bin`（12 片）显示「已完成 100%」。
- 批量栏文案正确汇总（本次 3 成功 0 失败）。
- 文件并发同时只有 2 条处于「上传中」，符合 `fileConcurrency=2`。

**结论**：✅ 通过

### S03 分片上传：切片、并发受控、进度

**步骤**
1. DevTools `emulate` 切到 **Slow 4G**（拉高 RTT，便于观察并发与进度）
2. 上传 `chunk-20mb-unique.bin`
3. 在「上传中」阶段高频抓取网络面板与进度条

**预期**：按 chunkSize 切片；`chunkConcurrency=2` 时同时最多 2 个 `POST /api/file/upload` 在途；进度百分比与实际已传字节一致。

**实际**
- 网络面板可见**恰好 2 个** `POST /api/file/upload` 同时处于 pending，前一完成才发起下一个，并发受控。
- 该会话下 RTT 较高，chunkSize 被 `resolveNetworkStrategy` 降到 512 KB，界面对应显示 **40 片**（20 MB / 512 KB），与切片数吻合。
- 进度百分比、瞬时速度、剩余时间同步刷新，进度 100% 时服务端已收齐全部分片。

**结论**：✅ 通过（注意：切片数会随网络策略变化，这一点在 S04 变成了缺陷）

### S06 暂停 / 继续

**步骤**
1. `emulate` 切到 **Slow 3G**
2. 上传 20 MB 文件，中途点击「暂停」
3. 观察状态与按钮，再点击「继续」

**预期**：暂停在分片边界生效，状态变「已暂停」，按钮变「继续 / 删除」；继续后从已传分片接着走。

**实际**
- 点击暂停后状态变「已暂停 0%」，按钮切换为「继续」「删除」。
- 点击继续后状态回到「上传中」，随后进度增长至 6%，速度 35 KB/s、ETA 均有值。
- 暂停期间网络面板无新的 `POST /api/file/upload`。

**结论**：✅ 通过（同会话内续传正常；跨刷新续传见 S04）

## 四、场景明细（失败项，含证据）

### S04 断点续传：上传中途刷新 + 重选同一文件 —— ❌ 失败

**步骤**
1. 上传 `chunk-20mb-unique.bin`（20 MB），记录刷新前的切片数与已传进度
2. 上传进行中**刷新页面**
3. 重新选择**同一个** `chunk-20mb-unique.bin`
4. 点击「开始上传」，观察是否跳过已传分片

**预期**：重新选择后，服务端按 `GET /api/file/status` 返回已存在分片，客户端只上传缺失分片。

**实际**（两层问题，均为失败）

**问题 1：分片键不稳定，字节级续传完全失效**
- 刷新前（Slow 4G，RTT 高）：界面显示 **40 片**，即 chunkSize ≈ 512 KB。
- 刷新后（网络策略重算，RTT 回落）：界面显示 **20 片**，即 chunkSize = 1 MB。
- 服务端分片键格式为 `${md5}_${size}_${chunkSize}`，`chunkSize` 变了 → 键变了 → `/api/file/status` 对新键返回 `chunks: []`。
- 结果：客户端**从头重传全部 20 个分片**（网络面板 reqid 225–244 连续 20 个 `POST /api/file/upload`），一个分片都没复用。

```
GET /api/file/status?...&chunk_size=1048576
响应: { "data": { "chunks": [] } }   // 旧的分片是 524288 的键，查不到
```

**问题 2：刷新后条目是「上传失败 0%」，不是可续传状态**
- IndexedDB 里的记录被还原，但状态直接落到 `上传失败 0%`。
- 点击「重试」后**没有任何网络请求发出**，仅弹出「重试上传失败」。
- 预期应出现的 `请重新选择文件以继续上传`（`messageApi.warning`）没有出现，用户拿不到可操作指引。

**结论**：❌ 失败
**新问题编号**：`E2E-01`（刷新后重试无网络请求且无引导）、`E2E-02`（chunkSize 每次会话重算导致分片键漂移、断点续传失效）

### S05 IndexedDB 暂存与恢复 —— ⚠️ 部分通过（判失败）

**步骤**
1. 建立 1 条「上传失败 / 未完成」记录
2. 刷新页面
3. 检查列表条数、进度、状态、可操作性

**预期**：刷新后列表还原，进度与状态与刷新前一致，且状态可支撑后续续传。

**实际**

| 检查项 | 结果 |
|---|---|
| 记录条数还原 | ✅ 还原 1 条（元数据持久化生效） |
| 进度还原 | ⚠️ 刷新前有进度，刷新后显示 **0%** |
| 状态还原 | ❌ 变成「上传失败」，语义错误（并非真失败） |
| 可操作性 | ❌ 重试无效（详见 S04 问题 2） |
| 文件字节是否可继续使用 | ❌ `fileRef` 仅存内存，刷新即失效，必须重新选择文件 |

**结论**：⚠️ 元数据还原可用，**状态/进度还原与可续传能力不可用**，整体判失败。
**关联**：`E2E-01`、`E2E-02`

### S07 取消上传（删除正在上传的文件）—— ❌ 失败（最严重）

**步骤**
1. 上传 `cancel-8mb-unique.bin`（8 MB）
2. 上传中点击该行的「删除」
3. 观察：行是否消失、后台是否真的停止、服务端分片是否停止增长
4. 先停后端、再恢复后端，观察该条目是否会回到列表

**预期**：删除后 Worker 任务被中止，不再发请求，服务端分片不再增长，条目不会复活。

**实际**
- UI 层表现正常：行消失，提示「文件已删除」。
- **但后台仍在继续上传**：服务端已收分片数在 20 秒内持续增长 `4 → 5 → 8`。
- 停掉后端再恢复后，该**已删除**的条目**重新出现在列表**，状态「上传失败 94%」。
- 点击「重试」后居然跑完，`server/uploads` 生成了 8 MB 文件：

```
3fe2aafdc095528ca43377f51110fcdb_8388608_262144_....bin   8388608   （8:04:33 落盘）
```

**控制台佐证**（后端不可用期间仍在重试）：
```
[rui-upload] 分片 10 上传失败: Error: HTTP 错误 502
```
（chunk 10 属于那个「已被删除」的 8 MB 任务，证明 Worker 里仍有它的在途任务）

**结论**：❌ 失败
**新问题编号**：`E2E-03`（删除不中止 Worker，且后台任务会把已删除条目写回列表并最终落盘）
**关联清单**：**VU-07**（取消/错误竞态）、**VU-01**（失败清理误删/残留文件）

---

### S12 后端不可用 / 网络中断 —— ❌ 失败

**步骤**
1. 停掉后端进程（Vite 代理开始返回 502）
2. 上传 `offline-512kb-unique.bin`（512 KB）
3. 观察 UI 反馈与耗时
4. 恢复后端，点击「重试」

**预期**：快速给出明确的失败提示（或明确的网络异常状态），不应长时间静默停留在「上传中」。

**实际**
- 行**长期停在「上传中 0%」约 27 秒**，期间无任何失败提示、无 toast、无错误态。
- 控制台仅有 Worker 内部日志：`[rui-upload] 分片 10 上传失败: Error: HTTP 错误 502`（这是别的残留任务，不是当前文件）。
- 后端恢复后，该文件变为「上传失败 50%」，点「重试」→「已完成 100%」，重试本身可用。

**结论**：❌ 失败（失败反馈缺失、状态滞后）
**新问题编号**：`E2E-04`（后端不可用时长时间无失败反馈，仅靠静默重试兜底）
**关联清单**：**VU-06**（预检失败跳过 status，使失败路径缺乏服务端状态校正）、**VU-07**

## 七、结论与建议

### 7.1 整体结论

- 上传主链路（选择 → 预检 → status → 分片 → 合并）**在正常网络、同一会话内是可靠的**，单文件、批量、分片并发、暂停继续、校验拦截、失败重试均通过。
- 但「刷新续传」与「删除中止」这两条**承诺给用户的可靠性能力实际上不成立**，并且会产出用户不期望的服务端副作用（已删除文件落盘）。

### 7.2 建议修复优先级

1. **E2E-03（P0）**：删除时对 Worker 任务发 `CANCEL` 并 `terminate` 兜底，同时给该 fileId 打 tombstone，禁止后台回调写回列表。
2. **E2E-02（P0）**：把 chunkSize 固化到任务记录里（随 fileId 持久化），后续续传统一使用记录中的值；或在服务端 `/status` 支持按 md5+size 跨 chunkSize 聚合已传区间。
3. **E2E-01（P1）**：刷新后状态应为「待继续 / 需重新选择」，而不是「上传失败」；重试时若无 `fileRef` 必须给出 `请重新选择文件以继续上传` 的明确引导，不能静默失败。
4. **E2E-04（P1）**：后端不可用应在有限时间内进入失败态并提示，而不是静默重试数十秒。
5. **S11（建议）**：确认是否需要 `allowedFileTypes` 白名单；若需要，当前配置无法拦截非法类型。
