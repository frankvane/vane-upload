## 4. 深入分析：VU-63-6「取消→继续→完成」与全量抖动

### 4.1 现象
初测时 VU-63-6 单独运行偶发失败，全量顺序运行时 VU-63-3/4/6/7 等**中断类用例**随机失败，失败点集中在「恢复后终态未达成」或「删除后仍存在合并产物」。带 `retries:1` 重跑仍失败（说明是确定性上下文失败而非随机抖动）。

### 4.2 定位手段
通过临时在主线程桥接层与控制器注入控制台日志（Playwright `page.on("console")` 捕获），逐用例追踪消息序列。关键取证：

```
[PROC] runUploadTask START ... status=uploading
[CANCEL-FILE] called ... status=uploading
[BRIDGE-RX] progress ...   （取消前在途分片进度）
[BRIDGE-RX] cancelled ...  （Worker 确认中断）
[PROC] runUploadTask DONE result={cancelled:true} kind=cancelled   → 置 PAUSED
[RESUME-FILE] resumeUploadTask alive=false                          → 走重新 processFileUpload
[BRIDGE-RX] done ... result={success:true, skipped:true}            → 命中「秒传」
```

由此确认：**「取消→继续」链路本身能正确收敛**，客户端最终拿到 `done`/`success`。失败的真实原因有两个：

### 4.3 根因一：闸口分片计数挂错对象，延迟/中止从未生效（测试程序缺陷）
`makeUploadGate` 曾把分片序号写在校验回调的 `route` 对象上：

```ts
route._n = (route._n ?? 0) + 1;
const n = route._n;
```

但 Playwright 对**每条请求都创建新的 `Route` 实例**，`_n` 永远从空开始 → **`n` 恒为 1** → `n >= 2` 的「延迟 / 中止」分支从不执行。也就是说闸口实际是空转，全部中断类用例都在「毫无节流的快速上传」上裸奔：上传转瞬完成并合并，`waitRowStatus('上传中')` 之后的操作（暂停/取消/删除）经常晚于合并，于是：
- 删除类用例：合并产物已生成、`abortServerChunks` 只清分片不清产物 → 「无产物」断言失败；
- 取消/暂停类用例：恢复时服务端已有完整文件 → 命中秒传，终态为 `秒传成功`，而旧断言只认 `已完成` → 等待 45s 超时。

机器越慢 / 用例越多，竞态窗口越偏移，故「单独跑过、全量随机挂」。

**修复**：将序号改为**闭包级共享计数器**，保证第 1 片放行、第 2+ 片真正进入延迟/中止。

### 4.4 根因二：异步路由句柄竞态（测试程序缺陷）
Worker 被 `terminate` 时在途请求随之取消，而闸口延迟回调随后仍会调用 `route.abort()/continue()`，此时 Playwright 抛 `Route is already handled!`。原写法 `try { void route.abort() } catch {}` **只捕获同步异常、不捕获 Promise 拒绝**，于是变成未处理的 rejection，直接把用例判失败。

**修复**：统一改用 `route.abort().catch(()=>{})` / `route.continue().catch(()=>{})`，显式吞掉已结束请求的拒绝。

### 4.5 产品侧加固：取消后 Worker terminate 而非回池
即便链路能收敛，仍存在一类隐患：取消后 Worker 的异步 `onmessage` 可能仍在执行并投递残留消息（`cancelled`/`debug`）。若把该 Worker 直接回空闲池复用，残留消息会被「取消→继续」重传时复用的同一 `worker.onmessage` 槽错误接收，导致新任务被误判为 `cancelled` 或丢弃其 `progress/done`。

**修复**：`uploadWorkerBridge.ts` 的 `cancelled` 分支补上 `shouldRecycleWorker = false`（与既有 `paused` 分支一致），取消后**销毁** Worker，彻底隔离残留异步消息。该改动为纵深防御，已在真实浏览器中回归通过。

### 4.6 断言口径修正
「暂停/取消 → 继续」的终态既可能是 `已完成`（真实续传 + 合并），也可能是 `秒传成功`（服务端已有完整文件、命中 md5+size 秒传）——**二者都代表产物已就绪且与源一致**。VU-63-3 / VU-63-5 / VU-63-6 统一改为接受这两种终态（VU-63-5 原本已如此）。

## 7. 已知限制

1. **仅覆盖 `simple` UI 模式**：E2E 入口固定 `uiMode="simple"`，未覆盖 `advanced`/完整模式下的按钮文案与状态 Tag，需后续补充。
2. **终态允许两种等价形态**：暂停/取消续传用例接受 `已完成` 或 `秒传成功`；这是产品合法终态，非放松校验。
3. **沙箱代理**：依赖 `NO_PROXY` 规避；迁移到真实代理环境需重新验证直连。
4. **产物 md5 比对基于后端合并文件**：若后续引入「合并后二次哈希/重命名」策略，断言需同步调整。
5. **删除类用例依赖可控延迟窗口**：通过 8s 延迟保证「删除发生在合并前」；若未来上传链路大幅提速或改造并发热点，需复核该窗口是否仍足够。
