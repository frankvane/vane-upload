> `server/src/app.js`、`server/src/middleware/auth.js`、`server/src/index.js`、`.dockerignore`。

## 1. 鉴权模式

| 检查项 | 结论 | 证据 |
|---|---|---|
| `AUTH_MODE` 默认值 | **`secure`**（不是 demo）。只有显式等于 `demo` 才关闭鉴权 | `server/src/config/index.js:68` `get("AUTH_MODE","secure")` |
| 未配置凭据时的行为 | fail-closed：仍以 `requireAuth: true` 挂载中间件，所有 `/api/file` 请求 401，并打 FATAL 日志 | `server/src/app.js:109-135`；`server/src/middleware/auth.js:112` |
| 启动期自检 | 仅在 `NODE_ENV` 非 development/test 时执行；缺凭据、`CORS_ORIGIN=*`、目录不可写都会启动即失败 | `server/src/index.js:21-30`、`server/src/config/index.js:137-173` |
| 容器内的值 | `ENV NODE_ENV=production`、`AUTH_MODE=secure` 已写死，符合基线 | `Dockerfile:24-27` |
| `.env.example` 的值 | `AUTH_MODE=demo`、`NODE_ENV=development` —— **仅供本地开发**，原样注入生产会全开接口 | `server/.env.example:6,13`（已补生产警示注释） |

⚠️ **唯一实质风险点**：代码默认值安全，但样例文件是 `demo`。进程管理器若自动加载 `.env`，
必须显式覆盖 `AUTH_MODE=secure` + `NODE_ENV=production`；不要直接 `cp server/.env.example .env` 上生产。

**凭据二选一（不可只配一半）**：

- Bearer：`FILE_AUTH_TOKEN=<长随机值>[,第二个值]` → 前端用 `getAuthToken()` / `getAuthHeaders()` 注入。
- Cookie：`FILE_AUTH_COOKIE=<cookie 名>` **且** `FILE_AUTH_COOKIE_TOKENS=<值白名单>`；
  缺后者时自检报错、Cookie 分支一律 401（`server/src/config/index.js:147-150`）。
  生产更推荐替换 `createAuthMiddleware` 为 portal_token 校验 + RBAC（`server/src/middleware/auth.js:3-5`）。

## 2. 卷与属主

| 检查项 | 结论 | 证据 |
|---|---|---|
| 进程用户 | **非 root**：`USER node` | `Dockerfile:36` |
| 目录属主 | 镜像构建期 `chown -R node:node /app/server`，覆盖 data / tmp/upload / uploads | `Dockerfile:34-35` |
| 持久化声明 | 三个状态目录都声明 `VOLUME`，必须挂持久卷，否则容器重建丢分片与 SQLite | `Dockerfile:38`；默认路径 `server/src/config/paths.js:23-25` |
| 可写性校验 | 生产启动时对三个目录 `mkdirSync(recursive)` + `accessSync(W_OK)`，不可写即 fail-fast | `server/src/config/index.js:160-169` |
| 镜像不含状态/密钥 | `.dockerignore` 排除 `.env*`、`*.log`、`server/data|tmp|uploads`、`**/*.sqlite*`、tests、docs | `.dockerignore` |

⚠️ **named volume / 匿名卷**：Docker 会用镜像内目录初始化，属主继承 `node:node`，可直接写。
**bind mount**：宿主机目录属主不会被镜像 `chown` 覆盖，若为 `root:root`，容器内 `node` 用户会写失败；
部署时需把宿主目录 `chown` 为镜像内 `node` 用户的 uid:gid，或改用 named volume。
启动自检会把这个问题报成 `目录不可写`，不会静默丢数据。

## 3. Cookie 模式：`SameSite` / CSRF

| 检查项 | 结论 | 证据 |
|---|---|---|
| 服务端是否下发 Cookie | **否**。`server/src` 中唯一的 `set-cookie` 字样是日志脱敏正则的字段名单，不是响应头 | `server/src/utils/logger.js:27`；全仓 `SameSite` 命中 0 次 |
| 服务端是否校验 CSRF | **否**。`server/src` 中 `csrf` 命中 0 次；中间件只按 Cookie 值白名单/`verify` 判定 | `server/src/middleware/auth.js:86-112` |
| Cookie 来源 | 只读取请求头 `Cookie: <FILE_AUTH_COOKIE>=...`，由**上游网关/登录服务**签发 | `server/src/middleware/auth.js:20-34,93-104` |
| CORS 默认 | 空 = 不返回 `Access-Control-Allow-Origin`；配了具体白名单才 `credentials: true`；`*` 在生产被自检拒绝 | `server/src/app.js:39-56`、`server/src/config/index.js:153-155` |

**结论：`SameSite=Lax/Strict` 与 CSRF 防护不在本仓库内，必须由签发 Cookie 的网关负责。**
这是报告 §5.3 / VU-21 标注的部署方责任，本次核对确认代码里确实没有任何替代实现。
最低要求：Cookie 带 `SameSite=Lax`（跨站 POST 不被携带）+ `Secure` + `HttpOnly`；
对 `/api/file/*` 这些状态变更接口再加 CSRF token 或 `Origin`/`Sec-Fetch-Site` 校验。
若走跨域，需同时配 `CORS_ORIGIN=<具体域名>` 且前端 `withCredentials: true`
（`src/shared/authHeaders.ts:82-84` 会把它翻成 `credentials:'include'`），**不能用 `*`**。

## 5. 部署前必须完成的动作

1. `NODE_ENV=production`、`AUTH_MODE=secure`，并配置 `FILE_AUTH_TOKEN` 或
   `FILE_AUTH_COOKIE` + `FILE_AUTH_COOKIE_TOKENS`；**不要原样使用 `.env.example`**。
2. 三个目录挂持久卷；用 bind mount 时先在宿主把属主对齐到镜像内 `node` 用户。
3. 仅当采用 Cookie 鉴权：网关侧设置 `SameSite=Lax`（或 Strict）+ CSRF 防护；
   跨域再配 `CORS_ORIGIN` 具体白名单 + 前端 `withCredentials: true`。
4. 按反代层级设置 `TRUST_PROXY_HOPS`（整数），否则限流失效。
