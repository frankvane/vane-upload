## 二、环境准备（P0，4 min）

### 2.1 启动后端（终端 1）

```bash
cd <项目根>
NODE_ENV=development PORT=3000 AUTH_MODE=demo RATE_LIMIT_ENABLED=false node server/src/index.js
```

- `AUTH_MODE=demo` 关闭鉴权，前端 demo 无需凭据；生产/联调请用 `secure` + `FILE_AUTH_TOKEN`。
- 就绪判据：`curl http://127.0.0.1:3000/api/health` 返回 `{"code":200,...}`。

### 2.2 启动前端（终端 2）

```bash
cd <项目根>
NO_PROXY=127.0.0.1,localhost npx vite --port 5173 --strictPort --host 127.0.0.1
```

- Vite 把 `/api` 代理到 `localhost:3000`。
- 若机器设置了 `HTTP_PROXY`，必须带 `NO_PROXY`，否则本地请求会走代理 502。

### 2.3 打开页面

- 地址：`http://127.0.0.1:5173/`
- 浏览器窗口宽度 **≥ 1000 px**：表格「操作」列固定在最右，宽度不足时需横向滚动才能看到行内按钮。

### 2.4 认识「测试注入口」（关键）

浏览器自动化（CDP/OS 层）**无法操作原生文件选择框**，因此 demo 页在开发环境挂载了一个注入面板
（`src/dev/fileInjectionPanel.tsx`，仅 `import.meta.env.DEV` 生效，生产与 `dist/lib` 库产物均不含）。
它用 `DataTransfer` 构造 `File` 并派发 `change` 事件，等效于用户真实选文件。

面板位置：**页面左下角**，标题「测试注入口（仅开发环境）」。

| 按钮 | 文件名 | 大小 | 分片数（chunkSize=1MB） | 用途 |
| --- | --- | --- | --- | --- |
| 小 512KB | 小-512KB.bin | 512 KB | 1 | 单分片最小通路 |
| 中 3MB | 中-3MB.bin | 3 MB | 3 | 常规多分片 |
| 大 12MB | 大-12MB.bin | 12 MB | 12 | 多分片 + 失败重试 |
| 中文名+空格 64KB | 中文名称 空格 文档.txt | 64 KB | 1 | 中文/空格文件名 |
| 含 test 名 4KB | test-被拦截示例.txt | 4 KB | 1 | 触发 customFileValidator |
| 11 个小文件 | 批量-1..11.bin | 64 KB ×11 | 1 | 触发 maxFiles=10 上限 |
| 3×40MB 队列 | 队列-1..3-40MB.bin | 40 MB ×3 | 40 ×3 | 制造稳定「上传中」窗口 |
| `[N]` + MB | 自定义-NMB.bin | N MB | N | 单个大文件（≤100MB） |

**「内容随机」勾选框**是秒传用例的开关：

- 勾选（默认）：每次注入内容不同 ⇒ 新 md5 ⇒ 真实上传。
- 取消勾选：内容按固定种子生成 ⇒ 同按钮重复注入 md5 相同 ⇒ 第二次命中**秒传成功**。

> 每个文件注入时 `lastModified` 都不同，避免被「同一文件重复选择」的内容指纹去重拦掉。

### 2.5 demo 页默认配置（`src/App.tsx`）

| 配置 | 值 | 影响用例 |
| --- | --- | --- |
| chunkSize | 1 MB | 分片数 = ceil(size/1MB) |
| fileConcurrency / chunkConcurrency | 2 / 2 | 多文件时出现「排队中」 |
| maxRetries | 3 | 失败重试次数 |
| maxFileSize | 100 MB | 超过即拒绝 |
| maxFiles | 10 | 超限整批拒绝 |
| autoUpload / autoCleanup / cleanupDelay | 开 / 开 / 5 s | 完成后记录会倒计时清理 |
| networkDisplayMode | tooltip | 徽标默认「简洁」 |
| customFileValidator | 名称含 `test` 或 >500MB 拒绝 | 校验用例 |

## 四、已修复缺陷（本轮发现并修复）

> 两条均已修复，并各自保留「复现路径」作为回归点；F4 用例即其人工回归入口，
> 自动化回归入口为 `e2e/upload.smoke.spec.ts` 的 `VU-63-12`（full UI 页面 `/e2e-full.html`）。

### F-01（已修复）｜整批「取消上传」后残留「上传中」死行

- **复现**：注入「3×40MB 队列」→ 上传中点「详情」→「取消上传」。
- **原现象**：传输已停（`上传文件` 恢复可用、`du -s server/tmp` 不再增长），但部分行仍显示
  `上传中` + 100% + **冻结速率**，既不能「继续」也不报错，只能删除或刷新；刷新后才自愈。
- **根因**：
  1. `cancelUpload` 只 `abort()` + 向 Worker 发 `cancel`，收尾完全押在 Worker 回 `cancelled` 上。
     Worker 若正卡在长同步哈希 / 大文件合并等待里收不到 `cancel`，桥接层的 800ms 兜底**只 terminate
     不结算**，`runUploadTask` 的 Promise 永不 settle → 状态机无收尾，行永久停在 `上传中`。
  2. 续传/重试链路（`resumeUploadFile` / `retryUploadFile`）发起的任务**没有 abort signal**，
     批级 `abort()` 根本触达不到，命中 (1) 的概率更高。
- **修复**：
  - `uploadWorkerBridge.ts`：新增 `taskSettleMap`（fileId → 强制结算回调），兜底路径改为
    「销毁 Worker **+ 结算任务**」；兜底回调用**回调身份比对**而非 fileId，避免「取消→立刻继续」
    时旧定时器误杀同一 fileId 的新任务；`dispose()` 也先结算在途任务。
  - `useBatchUploaderController.ts`：`cancelUpload` 改为「乐观落定」——对 `UPLOADING /
    PREPARING_UPLOAD / PAUSED` 的记录立即置 `PAUSED`、标记为用户取消（settle 后口径一致）、
    并把 speed/eta 归零，UI 立刻不再显示假死的速率。

### F-02（已修复）｜整批取消清空分片缓存，导致该行「继续/重试」失效

- **原现象**：整批取消后，该行再点「继续/重试」拿不到字节来源（刷新后直接判缓存缺失），
  界面只显示 `上传失败`，取消一次就把这行锁死。
- **根因**：`cancelUpload` 结束时对所有非终态记录调 `clearFileChunkCache`，
  本意是「防止刷新后自动拉起」，但把续传能力一起删了。
- **修复**：取消不再清缓存。「刷新不被自动拉起」改为由 `PAUSED` 语义保证——
  `isUploadableStatus()` 不含 `PAUSED`，只有用户显式点「继续」才会续传。

## 五、回归判定标准

一轮回归**通过**需同时满足：

1. A~F 全部用例的「预期结果」逐项命中；D 组允许因抢不到时序而重跑一次。
2. 浏览器控制台无 `pageerror`（未捕获异常）。
3. 后端 `/api/health` 全程 `code=200`，`chunkQueue.degraded=false`。
4. 缺陷区无回归：整批取消后**不得**残留 `上传中` 死行（F-01），取消后「继续」仍可完成（F-02）。

## 六、常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 页面能开但上传全失败 | 后端没起或 `AUTH_MODE` 不是 demo；先 `curl /api/health` |
| 请求 502 / 页面白屏 | 环境里存在 `HTTP_PROXY`，启动时补 `NO_PROXY=127.0.0.1,localhost` |
| 看不到「操作」列 | 浏览器窗口宽度 < 1000 px，拉宽窗口（或横向滚动表格） |

| 记录上传完就消失 | 「自动清理」开着且延时到了，属预期；回归时先关闭它 |
| 注入后全部秒传 | 「内容随机」没勾选，第二次同内容必然秒传 |
| 想验证服务端落盘 | `ls server/uploads/`，产物名形如 `u<hash>_<md5>_<size>_<chunkSize>_<md5>.bin` |

## 七、上传数量/大小限制（回归时按此对照）

### 7.1 组件库默认值 vs demo 页取值

| 限制项 | 组件库默认 | demo / E2E 页 | 作用与校验口径 |
| --- | --- | --- | --- |
| `maxFiles` | 100 | **10** | **列表内文件总数**（已有 + 本次选择），不是单次选择数；超限则**整批拒绝**（一个都不入队），提示「最多只能选择 10 个文件（当前已有 N 个）」 |
| `maxFileSize` | 100 MB | 100 MB | 单文件大小；超限提示「文件 "x" 大小超过限制 (100MB)」，该文件被跳过（其余合法文件正常入队） |
| `allowedFileTypes` | `[]`（不限制） | `[]` | 白名单为空表示全放行；非空时按扩展名/MIME 匹配，不匹配提示「文件 "x" 类型不被允许」 |
| 危险扩展名 | 内置清单 | 同 | 与服务端共用 `server/src/config/dangerous-file-types.json`，**选择阶段**即拦截，优先于白名单（不再"传完才 415"） |
| `customFileValidator` | 无 | 有 | 自定义同步校验，demo 里拦截文件名含 `test`、以及 >500MB |
| `fileConcurrency` | 2 | 2 | **同时上传的文件数**（不是总数上限）；多余文件停在「排队中」，前一个结束自动接续 |
| `chunkConcurrency` | 2 | 2 | 单文件内并发分片数 |
| `chunkSize` | 1 MB | 1 MB | 分片大小；改它会改变分片数（3MB → 3 片、12MB → 12 片） |
| `maxRetries` | 3 | 3 | 单分片失败重试次数，用尽才判该文件失败 |

> 关键结论：**「同时上传数」由 `fileConcurrency` 限制（默认 2），「能放多少条记录」由 `maxFiles`
> 限制（默认 100，demo 为 10），两者都不限制"一次会话累计上传过多少个文件"**——已完成记录被清理后可继续加。
> 多实例场景（同页多个 `<FileUpload>`）用 `instanceId` 隔离存储，各自独立计数，没有全局总量上限。

### 7.2 服务端上限（环境变量，与前端无关）

| 变量 | 默认 | 含义 |
| --- | --- | --- |
| `MAX_UPLOAD_SIZE_MB` | 5120（5GB） | 单文件上限（分片合计），超限 `/merge` 拒绝 |
| `MAX_CHUNKS` | 100000 | 单文件分片数上限 |
| `MAX_TOTAL_UPLOAD_SIZE_MB` / `MAX_TOTAL_CHUNKS` | 20480 / 200000 | 单次请求（一批分片）总量上限 |
| `MAX_USER_UPLOAD_SIZE_MB` / `MAX_USER_CHUNKS` | 10240 / 100000 | 单用户累计总量上限（分片会话级） |
| `CHUNK_MAX_SIZE_MB` | 20 | 单个分片大小上限 |
| `RATE_LIMIT_*` | 见 `server/src/config` | 接口限流；E2E 用 `RATE_LIMIT_ENABLED=false` 关闭 |

> 服务端**没有"文件个数"限制**，只有大小/分片/累计量限制——所以前端 `maxFiles` 是唯一的条数闸门。

## 八、上传回调清单（确认"上传后有没有回调"）

### 8.1 已接线、可用的回调

| 回调 | 触发时机 | 参数 |
| --- | --- | --- |
| `onUploadStart(files)` | 点「上传文件」/ 自动上传**开始一批**时（仅 `uploadAll` 路径；`批量重试` 不触发） | 本批可上传文件数组 |
| `onUploadProgress(file, progress)` | 上传中（已节流，同帧合并） | `progress` 0–100（**已标注 deprecated**） |
| `onUploadProgressDetail(file, detail)` | 同上，推荐使用 | `{progress, uploadedBytes, totalBytes, speed, eta}` |
| `onUploadComplete(file, success)` | **成功**收尾（`已完成` 与 `秒传成功` 都会触发，`success=true`） | 最新记录 + `true` |
| `onUploadError(file, errorMessage)` | **失败**收尾（终态 `上传失败`） | 最新记录 + 错误文案 |
| `onBatchComplete({success, failed, total})` | 一批正常跑完后的批次结算（整批取消/中止时**不触发**） | 计数三元组 |
| `customFileValidator(file)` | 选择文件阶段同步校验 | 返回 `{valid, message}`，用于自定义拦截 |

> **重要边界**：`暂停`、`取消`、`删除` 这三条路径**不会**触发上述任何"完成/失败"回调——
> 它们只改行状态（`已暂停` / 记录移除）。需要感知这些动作请以 UI 状态或 `onUploadProgress` 停止为准。

### 8.2 声明了但**未接线**的回调（已知缺口）

| 回调 | 现状 |
| --- | --- |
| `customUploadHandler(file, config)` | 仅在 `types/upload.ts`、`UploadContext`、`useEffectiveConfig` 中透传，**运行时从未被调用**（全仓库无调用点）。传了也不会生效，属"看起来能自定义上传、实际无效"的坑；下次迭代要么实现（绕过 Worker 走自定义上传），要么从 props 中移除，避免误导。 |
