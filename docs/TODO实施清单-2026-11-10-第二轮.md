## 2. D 决策详情（2026-11-10 已拍板）

> 三项均按「方案 A」定案，其中 D-04 / D-06 对原方案 A 有细化（见各自结论）。
> 决策只定方向，**不改生产代码**；落地分别由 T-31 / T-57 / T-41 执行。

**D-04｜相对 `baseURL` 下鉴权头白名单采用哪种语义**　✅ **已定：方案 A + 三条约束**

- 复核结论（确认的功能失效）：`normalizeHost("/api")` 走 `new URL("https:///api")` 得到 host `"api"` → 白名单 `["api"]`；`joinUrl("/api", checkApi)` 产出 `/api/file/check`；`isUrlAllowed` 用 `new URL(相对URL)` 解析抛错 → `false` → `sendAuth=false`。所有请求漏发 `Authorization`，相对 base 部署必 401。`url.test.ts:50-53` 已把相对 base 写成公开契约，方案 B 属破坏性升级，不采纳。
- 定案语义：
  1. `normalizeHost` 对相对形式（`/`、`./`、`../` 开头，或无协议无 host）返回 `null`，语义是**同源**而非「无效」；绝对 URL / 裸 host 逻辑不变。
  2. `isUrlAllowed(url, allowedHosts, baseOrigin?)` 增加**显式注入**的 `baseOrigin`，相对 URL 用 `new URL(url, baseOrigin)` 解析；模块内**不读 `self.location`**，保住纯函数可测性与 Node 测试环境。Worker 调用点传 `self.location.origin`。
  3. 空白名单不再无条件 `return true`，改为「仅同域允许」；`//host/...` 协议相对 URL 一律按外域处理，防 `joinUrl("", "//evil.com/x")` 绕过。绝对 URL 仍按 host 白名单比对。
- 下游：T-31 按此落地，README 的 `baseURL` 配置行补「相对 base 视为同源」。判据：`isUrlAllowed("/api/file/check", [], "https://app.example.com")` 为 `true`；`isUrlAllowed("//evil.com/x", [], 同源)` 与 `("https://other.com/x", [], 同源)` 均为 `false`。

**D-05｜暂停 / 续传架构二选一**　✅ **已定：方案 A（统一「暂停即重跑续传」）**

- 复核结论：`uploadWorkerBridge.ts:400-413` 收到 `paused` 即 `shouldRecycleWorker=false` 并 terminate，Worker 永远收不到 `resume`；`uploadWorker.pause.test.ts` 的 2 条直测绕过 bridge 直接给 Worker 发消息，因此「测试绿、线上死」。用户可见语义「暂停 → 继续 → 断点续传」由服务端 `/check` 保证，不依赖 Worker 挂起。
- 定案范围：
  1. **删**：`taskPauseState`、`waitWhilePaused`、`pause` 分支里的挂起逻辑、`resume` 分支、`chunkPipeline` 的 `isPaused` / `waitWhilePaused` 参数、`workerProtocol.ts:62-68,119-129` 的 `resume` / `resumed` 消息类型，以及 `uploadWorker.pause.test.ts` 2 条死路径直测。
  2. **留**：`paused` 回传与 `pausedChunks` / `totalChunks`（UI「已暂停」行与进度依赖）、bridge 的 terminate 决策。
  3. **不取消**：T-57 中「terminate 打断未走到 `deleteCachedChunk` 的 IDB 事务」是独立数据一致性缺陷，与选 A/B 无关。
  4. 行为护栏：e2e `VU-63-3 暂停后继续并完成，产物 md5 一致` 已存在；T-57 补一条「继续后已上传分片数不倒退」断言。
- 不采纳 B：B 是让实现去追一段从未启用的设计，收益仅省一次 Worker 启动 + 一次 `/check`，却要同时解决静默看门狗误杀、回池挂起闭包、Map 生命周期与 T-63 依赖重排，与「不猜测性优化」冲突。若日后实测证明重跑成本显著，另开议题。

**D-06｜体积门禁口径**　✅ **已定：方案 A，但按模块格式分组独立判定**

- 复核修正（原方案 A 的计量口径不成立）：`package.json files:["dist/lib"]` 确认 14 个 JS/CSS 全部发布，但 `exports` 的 `import` / `require` 只会加载其中**一组**。`dist/lib` 里 ESM / CJS 各有一套动态 chunk，`98.24KB` 把同一份代码算了两次，按它设总预算会严重失真。
- 实测（gzip，CSS 共享只计一次）：**ESM 组 49.28 + 4.52 = 53.80KB**；**CJS 组 44.44 + 4.52 = 48.96KB**；入口 `index.js` 19.31KB / `index.cjs` 17.04KB。分包源头是 `src/components/ZustandFileUpload/index.tsx:25-26` 的两个 `lazy`（原描述写的 `index.tsx:25,27` 已校正）。
- 定案口径：
  1. 遍历 `dist/lib` 全部 `.js` / `.cjs` / `.css`，按格式分两组（`.js`+CSS = ESM，`.cjs`+CSS = CJS），**每组独立判定**；
  2. 单组总预算 `SIZE_LIMIT_FORMAT_KB = 65`（余量 21% / 33%），保留单入口 `SIZE_LIMIT_KB = 40`；
  3. 陈旧产物守卫从 2 个入口扩展到全部文件。
- 下游：T-41 按此落地并更新 §9 附录 A 基线。判据：给任一动态 chunk 塞 100KB → 对应格式组 153.8KB > 65KB 变红，恢复后变绿（满足 L1-1 变异）。
- 不采纳 B：`inlineDynamicImports` 会把首包从约 19KB 推到约 49KB，且消费方失去按需加载 `FileTable` / `StorageStatsDrawer` 的能力，为省门禁复杂度付运行时代价。

**目标**：消除预热全量 put 与 Worker 逐片 delete 乱序导致「已确认分片被写回成为孤儿分片」的数据一致性缺陷（L3-2）。

**根因**：主线程预热（`chunkCache.ts` `runPrime` 的 `while (index < chunkCount)`）写全部分片，上传 Worker 每确认一片即 `deleteCachedChunk`（chunkPipeline.ts:165）释放本地缓存，合并完成后再 `deleteFileCache`（:322）全清——两条链路都 fire-and-forget 且跨线程（主线程 / Worker 各持一份 IndexedDB 引用），无协调。若预热在上传清理之后写回分片（大文件预热慢于上传时必现），已确认分片会作为孤儿分片留存于 chunks store，且 `index < uploadedChunks` 仍残留。
