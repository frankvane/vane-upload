## 2. D 决策详情

**D-01｜0 字节文件是否允许上传**

> **结论（2026-11-10 拍板）：不允许。** 走方案 A —— 前端选择阶段直接拒绝，提示「文件 "xxx" 为空文件，不支持上传」。

- 背景：前端有专门用例支持空文件（`chunkCount = 0`），后端 `/merge` 要求 `total ≥ 1` 必 400，端到端不一致（报告 P2-10）。
- 方案 A（**采用**）：前端选择阶段直接拒绝 —— 改动最小，且错误发生在用户刚选完文件时，提示最及时。
- 方案 B（未采用）：后端支持 `total = 0` —— 语义虽完整，但要改校验 + 分片合并 + 补后端用例，且与「上传即产出有效文件」的产品假设相悖。
- 下游：**T-12 已按方案 A 落地**（见 §4）。

**D-02｜后端错误文案用中文还是错误码**

> **结论（2026-11-10 拍板）：中文。** 走方案 A —— 后端 4xx/5xx 兜底文案全部中文化，与 README「`message` 请写成中文」的契约对齐。

- 背景：README 约定中文，实现全英文，前端最终展示成 `HTTP 错误 400: total must be a positive integer`（报告 P3-6）。
- 方案 A（**采用**）：后端文案中文化 —— 无需前端维护错误码映射表，契约与实现一致。
- 方案 B（未采用）：英文 message + 前端按错误码映射 —— 需要前后端同步维护映射表，且现有 41 处文案已覆盖绝大多数场景，映射表收益低。
- 下游：**T-13 已落地**（见 §4），并同步了 9 处测试断言。

**D-03｜主干分支保留 `master` 还是迁移 `main`**

> **结论（2026-11-10 拍板）：保留 `master`。** CI 直接监听 `[master]`，不做分支迁移。

- 背景：CI 监听 `main`，仓库默认分支 `master`（报告 P1-1）。
- 下游：**T-01 已按 `[master]` 落地**（见 §3），未采用双写——既然不迁 main，留 `main` 只会让配置长期含死分支。

**T-16｜新增首字节延迟预算用例**　`性能` `半天`　**（依赖：✅ T-05 / ✅ T-29）**

- **口径为什么这样定**（两轮否定后）：
  - 绝对值（原「100MB ≤ 2s」）→ 作废：1KB 首字节就有 651–722ms，绝对值永远为真。

  - 最终口径：`固定开销 = 首字节 − Worker 实测哈希 − 实测合并窗口`，只对这个残差设预算。

- **两条断言**：
  1. `固定开销(48MB) − 固定开销(8MB) ≤ 100ms` —— 启动链路的**体积相关系数**，基线 ≈0（实测 −5~14ms）。
     这是 P1-2 的哨兵：任何「上传启动前等整文件读盘/读入」的回退都在这里爆。
  2. `固定开销(1KB) ≤ 500ms` —— 固定开销总量，基线 146–223ms（dev）/ ≈63ms（prod）。

**T-29｜首字节固定开销归因**　`P2` `半天`

- 位置：`useFileProcessor.ts:404-412`（`setTimeout(uploadAll, 500)`）、`worker/filePrepareWorker.ts:74-126`（全量 md5）
- 做法：新增 `src/shared/perfTrace.ts`（`globalThis.__VANE_PERF_TRACE__ === true` 才生效，默认零打扰），
  在 6 个主线程阶段点 + Worker 内部 3 段时间上打点；Worker 通过 `complete.timings` 回传
  `{ boot, waitForMessage, hash }`；测量脚本 `e2e/perf.first-byte.spec.ts`（`PERF_TRACE=1` 才纳入，
  常规 e2e 仍是 11 条），支持 `PERF_PROD=1` 在生产构建上复测。
- **实测（生产构建，3 次中位数，1KB / 8MB / 48MB）**：

  | 阶段 | 1KB | 8MB | 48MB | dev 1KB（对照） |
  |---|---|---|---|---|
  | change → 校验完成 | 0 | 0 | 0 | 0 |
  | 校验 → 建预处理 Worker | 1 | 0 | 0 | 0 |
  | Worker 启动 + 哈希（boot / hash） | 15（6 / 1） | 142（7 / 118） | 719（15 / ~700） | 37（34 / 2） |
  | 哈希剩余 → complete | 2 | 1 | 2 | 5 |
  | 持久化 + 刷新队列 | 8 | 12 | 9 | 28 |
  | **自动上传合并窗口** | **508** | **505** | **513** | **506** |
  | 派发 → 上传 Worker 启动 | 14 | 35 | 41 | 42 |
  | 派发 → 首个网络请求 | 23 | 19 | 22 | 45 |
  | **合计 change → 首个请求** | **571** | **711** | **1329** | **664** |

  **不是 Worker、不是哈希、不是 IDB**；真正工程开销合计 ≈63ms。
  ② 体积相关的唯一真实成本是全量 md5 ≈**14.6ms/MB**（2GB ≈ 29s），dev 与 prod 一致 → 算法问题，非构建问题。
  ③ 原假设「700ms 落在 Worker 预处理段」**被推翻**：prod 下 Worker 启动只要 6–15ms。
- 判据达成：产出分段实测表 + 明确主导段；且**没有**顺手做任何猜测性优化（`hashMode` 默认值、Worker 保活均未动）。

**T-30｜自动上传合并窗口（500ms）是否可配置**　`决策` `1h`　**✅ 已决（2026-11-10）：选「降低时长」= B + C**

- 现状：`useFileProcessor.ts:404-412` 写死 `setTimeout(() => uploadAll(), 500)`，
  仅在 `autoUpload` 时生效；作用是让「连续快速选几次文件」合并成一批上传。手动点「开始上传」不经过它。
- 实测代价：它是 1KB 场景首字节的 **89%（508 / 571ms）**，与体积无关。
- 三个选项（按侵入性排序）：
  - **A 保持现状（默认推荐）**：不改代码，只在 README 的「首字节/延迟口径」里写明这 500ms 的存在，
    避免后来人再把它当性能 bug 排查一遍。
  - **B 暴露 `autoUploadDelay` 配置（默认仍 500）**：约 10 行 + 1 条用例，消费方可自行调 0；
    语义与现状兼容，风险最低的「可配置化」。
  - **C 默认降到 0–100ms**：连续两次选择会变成两批 → 服务端多一轮 `/merge`，
    且「一次拖多个文件」不受影响（仍在同一批）。**属产品行为变更，需明确授权。**
- 判据：拍板后若选 B/C，新增用例证明「两次选择间隔 < delay → 合并为一批；> delay → 两批」，
  并同步 README 的配置表与首字节口径。
- **明确不做**：拍板前不允许任何人为了「首字节数字好看」直接改这个常量 —— 这是行为变更，不是性能优化。
- **决策（2026-11-10 用户拍板）**：「最好下降时长」→ 同时做 B + C：
  新增 `autoUploadDelay` 配置（可回退到 500），**默认值下调到 120ms**。
- **落地**：
  - `types/upload.ts`：`autoUploadDelay?: number`（props + `UploadConfig` 双处），
    新增 `DEFAULT_AUTO_UPLOAD_DELAY_MS = 120` 并写明为什么是 120 而不是 0；
  - `UploadContext` 解构默认值 → `useEffectiveConfig` 透传 → `useFileProcessor` 用它替换写死的 `500`；
  - `resolveAutoUploadDelay()` 做取值保护：负数 / `NaN` / `Infinity` 回落默认（`Infinity` 会让
    `setTimeout` **永不触发** = 自动上传静默失效，这是最需要防的一种），上限 5000ms。
- **实测收益（生产构建，3 次中位数）**：

  | 体积 | 改造前（500ms 窗口） | 改造后（120ms） | 差 |
  |---|---|---|---|
  | 1KB | 571ms | **210ms** | −361ms（−63%） |
  | 8MB | 711ms | **340ms** | −371ms |
  | 48MB | 1329ms | **1211ms** | −118ms（哈希主导，占比被稀释） |

  分段看：合并窗口 508 → **129ms**，其余段（Worker 启动 6–19ms、持久化 19–21ms、派发→首请求 27–31ms）不变 —— 说明省下的正是那部分。
- **行为代价（已写进 README）**：间隔 > 120ms 的两次选择会变成两批，服务端多一轮 `/merge`；
  「一次选多个文件」不受影响（同一批只有一个 `change` 事件）。需要旧观感时显式传 `autoUploadDelay={500}`。
- **用例（6 条，`useFileProcessor.test.tsx`）**：窗口内第二次选择被合并、只开跑一次；`delay=0` 时两次选择各自开跑；
  `Infinity`/负数/`NaN` 三个脏值都回落默认且能到点；`autoUpload=false` 时窗口完全不参与。
  变异自查：把 resolver 换成 `Math.min(delay ?? 500, 5000)` → 4 条用例变红（含默认值与三个脏值）。

## 6. 明确不做（防止"为简化而简化"）

以下四处在报告中被判定为**正确取舍**，任何人提"优化"时应先回看本节：

| 对象 | 为什么不动 |
|---|---|
| `uploadWorkerBridge` 的 `taskSettleMap` / `CANCEL_FALLBACK_MS` / 静默看门狗 | 每条都对应真实卡死场景，删任一条会回归「行永久停在 100%」 |
| `uploadWorker` 的 `isCancellation` / `isConnectionFailure` / `isBackendUnavailable` | 三段语义细分让错误文案可执行，合并会退化体验 |
| `shared/concurrency.runCursorPool` | 游标式把内存从 O(分片数) 降到 O(1)，不要为"可读性"改回数组 map |
| `uploadAll` 的 IDB 全表 `iterate`、`patchFile` 的 O(n) `map` | n ≤ 100，收益与风险不匹配（报告 §4.3 已判定） |
| `primeChunkCache` 的逐片门闩（报告原提议的 `whenReadyThrough`） | 就绪标记是最后写入的，「第 i 片已落盘」不改变任何可观测行为；加它只会多一套跨线程门闩协议 + 「预热卡住 → 上传永久等待」的新失败模式。详见 T-05 的偏离说明 |
| `autoUpload` 合并窗口的**默认值**（现 120ms，T-30 已拍板下调） | 它是行为（连续选文件是否合并成一批），不是性能缺陷。要改这个默认值必须重新走产品决策，并同步 README 配置表 + 那 6 条合并窗口用例；**不允许为了首字节数字好看擅自再调低**（调低后「连续两次选择」会拆成两批，多一轮 `/merge`） |
| 预处理 Worker 保活 / 预建 | T-29 实测 prod 下 Worker 启动仅 6–15ms，收益上限 15ms，代价是常驻空闲 Worker；不划算 |
