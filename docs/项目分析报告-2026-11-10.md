### 1.4 主链路

```
选择文件
  → filePrepareWorker（全量/采样哈希，流式，内存与文件大小无关）
  → 去重（hash+size+lastModified+name）+ 重绑（刷新后残留记录复用 id / chunkSize）
  → 落 IDB 元数据 + primeChunkCache（把待传分片全量写进 IndexedDB）★ 关键成本点
  → autoUpload（500ms 防抖）→ uploadAll
       → 每实例 workerPool 取一个 Worker
       → Worker: /instant 轻量预检（命中即秒传，不算任何分片 MD5）
                → /status 查询已存在分片（失败退化为全量重传）
                → 游标池并发上传缺失分片（按需算 chunk md5）
                → /merge 合并
       → 每片确认后删除对应缓存（占用随进度下降）
  → 状态回写（IDB + store 内存同步）→ 自动清理倒计时
```

## 2. 架构评审

### 2.1 最值得保留的设计：每实例引擎

`UploadProvider`（`context/UploadContext.tsx:106-118`）用 `useMemo([instanceId])` 一次性创建
`{ instanceId, storage, fileRegistry, workerPool, store }`，经三层 Context 下发。

这一处决定了三件事：

- 同页多实例天然隔离（各自的 IDB storeName、各自的 Worker 池、各自的队列）；
- 卸载时只 dispose 自己的资源，不会像模块级单例那样"一个实例卸载、全部实例瘫痪"；
- `useUploadStore(selector)` 的调用方式与旧单例版本完全一致，改造对下游零侵入。

配套的 `createUploadWorkerPool`（`services/uploadWorkerBridge.ts:105`）同样是工厂，且引用了
**按任务身份比对而非按 fileId 比对** 的兜底（`taskSettleMap`，第 157-181 行）——这解决了"取消 → 立刻继续"
时旧定时器误杀新任务的问题。这类细节说明作者踩过真实竞态。

### 2.2 状态机

8 个状态（`types/upload.ts:5-22`）+ 两条刻意设计的规则：`PAUSED` 与 `ERROR` 都**不**属于"可自动上传"集合
（`uploadStorage.isUploadableStatus`），避免刷新后被顺带重跑。转换矩阵见 §7.6。

### 2.3 前后端契约

`{ code, message, data }`，客户端以 HTTP 状态码判定成功（`message` 直接面向用户）；
5 个业务接口 + `/health`。约定式推导两处：`checkApi` → `/status`、`uploadApi` → `/abort`
（`uploadWorker.ts:586-589`、`useFileOperations.ts:19-22`）。这是可用的务实做法，但属于隐式契约 —— 见 §3 P3-2。

### 2.4 前后端职责分配（合理）

| 关注点 | 前端 | 后端 |
|---|---|---|
| 危险扩展名 | 选择阶段拦截（与服务端共用 `dangerous-file-types.json`） | `/merge` 前 415 兜底 |
| 完整性 | full 模式全量 MD5 | size + 逐分片 md5 + 合并后再算一次全量 md5 |
| 配额 | 按 `navigator.storage.estimate` 决定是否缓存 | 单文件 / 全局 / 用户三维封顶（DB 聚合，重启安全） |
| 续传 | `/status` + 分片缓存 | `/status` + `reconcileChunksWithDisk` 磁盘对账 |

### P1-1 CI 监听分支与默认分支不一致

- **触发条件**：任何 `git push origin master`。
- **证据**：`.github/workflows/ci.yml:3-5` 为 `on.push.branches: [main]`；`git branch -a` 显示
  `remotes/origin/HEAD -> origin/master`，本地与远端主干均为 `master`。
- **影响**：`npm run ci`（typecheck / lint / test:coverage / server test / build / size-check）在主干上
  从不自动执行，只有 PR 才触发。主干回归只能靠人工本地跑，等于门禁半失效。
- **修复**：`branches: [main, master]`，或直接改 `[master]`（若计划迁到 main，则先迁分支再改配置）。
- **验证**：推送一个空提交后看 Actions 是否出现 run；或 `gh workflow list --all` 对照默认分支。

### P1-2 首字节延迟与文件大小线性相关 —— ✅ 已修（T-05），但实测推翻了原判断的量级

- **证据链（改前）**：
  1. `useFileProcessor.ts:321-328` 选文件即 fire-and-forget `primeChunkCache`（写全部待传分片）；
  2. `useBatchUploaderController.ts:133-137` 上传启动前 `await primeChunkCache(...)`，**未完成不置 `UPLOADING`**；
  3. `chunkCache.ts:186-206` 逐批（16 片/事务）`fileRef.slice().arrayBuffer()` + `putCachedChunks`。
- **原量级估算**：认为成本 ≈ 读 N 字节 + 写 IDB N 字节，100MB 约 0.5–1.5s 纯等待。
- **实测（本机，e2e 页面 + Playwright `page.route` 记录首个 `/api/file/upload` 时刻，dev 模式）**：

  | 文件大小 | 改前（启动前 await 全量预热） | 改后（预热并行） | 说明 |
  |---|---|---|---|
  | 1KB | — | **749ms** | 固定开销基线（与体积无关） |
  | 8MB | 1058ms | 766 ~ 1091ms | 差异落在噪声内 |
  | 48MB | 1683ms | **1532ms** | 省 151ms ≈ 3ms/MB |

  **结论：预热在关键路径上的实际贡献 ≈ 3ms/MB（48MB ≈ 150ms），而首字节有 ~700–750ms 与体积无关的固定开销。**
  （这 700ms 后由 **T-29 归因**：508ms 是 `autoUpload` 的 500ms 合并窗口，工程开销只有 ≈63ms —— 详见 P2-11。）
  原估算的 0.5–1.5s 高估了 3–10 倍，因为它按「磁盘吞吐 100–300MB/s」推算，而实际 IDB 写入与预热是重叠在主线程线程池里的异步 IO，且分片缓存写入被浏览器并发调度。

- **修复（已落地）**：会话内上传不再等预热 —— `fileRef` 存在时 `void primeChunkCache(...)`，
  只有「刷新后续传」（`fileRef` 缺失、缓存是唯一字节来源）仍必须等到 `isFileCacheReady` 为真。
  **没有**按原方案实现 `whenReadyThrough(index)` 的逐片门闩：就绪标记是最后写入的，
  逐片门闩不会改变任何可观测行为，只会增加跨线程协议与「预热卡住 → 上传永久等待」的新失败模式。
- **代价（已写入清单）**：预热窗口内刷新 → 无就绪标记 → 走既有「需重新选择」降级。
  窗口长度 = 3ms/MB（2GB ≈ 6s）。这条不是新增失败模式，但与原来「上传开始后零点击续传必可用」不同。
- **判据修正**：原文写「首字节 <100ms」，在 dev 下不可能达成（固定开销就 750ms）。
  改为「**随体积的增量** ≤ 单分片量级」——比较 8MB 与 48MB 的差值，而不看绝对值。
- **连带发现 → P2-11**：真正的首字节大头不在预热。见下条。


### P2-11 首字节固定开销已归因：508ms 是「自动上传合并窗口」，不是 Worker（T-29 结案）

> 本节已由实测结论替换原推测。原判断「700ms 落在 Worker 预处理段」**被数据推翻**，
> 推翻过程保留在下方「为什么原来会误判」，因为这条误判本身比结论更有信息量。

- **怎么量的**：新增埋点模块 `src/shared/perfTrace.ts`（`globalThis.__VANE_PERF_TRACE__ === true`
  才生效，默认零打扰），在 `handleFileChange` 的 6 个阶段点 + 预处理 Worker 内部 3 个耗时上打点，
  用 `e2e/perf.first-byte.spec.ts` 跑「change → 首个 `/api/file/instant`」，每个体积 3 次取中位数。
  Worker 内部耗时随 `complete` 消息回传（`timings: { boot, waitForMessage, hash }`）。
- **实测（生产构建 `dist/demo`，中位数）**：

  | 阶段 | 1KB | 8MB | 48MB | dev 1KB（对照） |
  |---|---|---|---|---|
  | ① change → 校验完成 | 0ms | 0ms | 0ms | 0ms |
  | ② 校验 → 建预处理 Worker | 1ms | 0ms | 0ms | 0ms |
  | ③ Worker 启动 + 哈希（boot / hash） | 15ms（6 / 1） | 142ms（7 / 118） | 719ms（15 / ~700） | 37ms（34 / 2） |
  | ④ 哈希剩余 → complete | 2ms | 1ms | 2ms | 5ms |
  | ⑤ 持久化 + 刷新队列 | 8ms | 12ms | 9ms | 28ms |
  | ⑥ **自动上传合并窗口** | **508ms** | **505ms** | **513ms** | **506ms** |
  | ⑦ 派发 → 上传 Worker 启动 | 14ms | 35ms | 41ms | 42ms |
  | ⑧ 派发 → 首个网络请求 | 23ms | 19ms | 22ms | 45ms |
  | **合计 change → 首个请求** | **571ms** | **711ms** | **1329ms** | **664ms** |

- **结论一（固定开销的真身）**：`autoUpload` 生效时，`complete` 之后有一段
  `setTimeout(() => uploadAll(), 500)`（`useFileProcessor.ts:404-412`，用于把连续多次选文件合并成一批）。
  它在 1KB 场景占 **508 / 571 = 89%**。**工程开销合计只有 ≈63ms**
  （Worker 启动 6ms + 持久化 8ms + 派发与上传 Worker 启动 14ms + 到首个请求 23ms），
  其余 2ms 是哈希。**因此「首字节慢」不是代码慢，是设计上的合并窗口。**
- **结论二（体积相关的成本）**：全量 md5 稳定在 **≈14.6ms/MB**（8MB 118ms、48MB ≈700ms，
  dev 与 prod 几乎一致 → 不是构建模式问题，是单线程 spark-md5 的固有成本）。折算 2GB ≈ 29s，
  这才是大文件场景唯一值得动的地方。
- **结论三（dev 为什么看起来更糟）**：dev 与 prod 的差异只集中在 ③⑤⑦⑧（Worker 启动 34→6ms、
  持久化 28→8ms、派发 42→14ms、到首请求 45→23ms），而 ⑥ 定时器与哈希速率两侧一致 ——
  所以 T-05 那次「dev 下看起来更慢」的观感，一半是 500ms 窗口，一半是模块拆分开销。
- **为什么原来会误判**：T-05 只测了「1KB 首字节 749ms」这一个总数，看到它落在
  「change → 首个网络请求」之间，就按代码顺序把候选嫌疑排到了 Worker 预处理段。
  实际那 749ms 是到 `/api/file/upload` 的时间，比本表的 `/api/file/instant` 多出
  「秒传预检 + 状态查询 + 分片 md5」约 85ms；减去之后剩下的 664ms 里 500ms 是纯定时器。
  **教训：不给时间轴分段，"按代码顺序猜"必然把定时器算成 CPU。**
- **对 T-16 的直接影响**：预算必须建在**残差**（扣掉哈希与合并窗口）上，而不是总耗时 ——
  `e2e/first-byte.budget.spec.ts` 已按此实现：体积增量 ≤100ms（P1-2 哨兵）+ 1KB 固定开销 ≤500ms。
  另有一个反直觉盲区：把预热改回 `await` 时该预算**不会红**（48MB 预热 ≈144ms 被 500ms 窗口吸收），
  该场景由 T-05 的单测守护。
- **明确不做（避免下一轮凭直觉动手）**：
  - **不改** `hashMode` 默认值 `full → sample`：这是产品决策（采样碰撞会让秒传低概率误命中，
    服务端校验强度随之下降），不由工程单方面改。
  - **不做**「空闲时预建并保活预处理 Worker」：prod 下 boot 只 6–15ms，收益上限 15ms，
    代价是常驻空闲 Worker 的内存与生命周期复杂度，不划算。
  - **不擅自缩短** 500ms 合并窗口：它决定了「连续快速选多次文件是否合并为一批」，
    交给产品决策（清单 T-30）。**注意它只在 `autoUpload` 时存在**，手动点「开始上传」没有这段。

## 4. 性能分析（React 19 + Vite 语境）

### 4.1 规则适用性先对齐

| react-performance 分类 | 本项目是否适用 | 说明 |
|---|---|---|
| 1 消除瀑布 `async-*` | ⚠️ 部分 | 无 RSC，但 Worker 内 `/instant` → `/status` → 分片 → `/merge` 是真实串行链；已做"预检命中即短路"与"按需算 md5" |
| 2 包体积 `bundle-*` | ✅ 适用 | 内部 `lazy` 分包、具名导入、90KB gzip 门禁 |

### 4.4 组件库场景下的 Core Web Vitals

组件库本身没有 LCP/INP 指标，但宿主页面的指标会被它影响。映射关系：

| 宿主指标 | 本组件的主要影响因素 | 当前状态 |
|---|---|---|
| LCP | 首屏 JS 体积 | ✅ 19.21KB gzip（重建后实测）+ 表格/抽屉懒加载 |
| INP | 进度更新频率、列表行数 | ✅ 50ms 节流 + 单元格级订阅 |
| CLS | 表格行出现/消失、自动清理 | ⚠️ 自动清理默认 10s 后移除行会引起跳动（`autoCleanup` 可关） |
| TBT | 哈希计算、IDB 批量写 | ✅ 哈希在 Worker（但全量 md5 ≈14.6ms/MB，大文件仍占主线程外的时间预算）；✅ 预热已移出上传关键路径（T-05）；✅ 首字节固定开销已归因（T-29）：508ms 是自动上传合并窗口、63ms 才是工程开销（P2-11） |

### 4.5 建议加的两条预算

- **构建体积预算**：现有 90KB 门禁偏松（重建后实际 19.21KB）。建议降到 40KB，给未来功能留空间同时防劣化。
- **首字节预算（已落地，T-16）**：原「100MB → 首个 `/upload` ≤ 2s」与「体积差值 ≤300ms」两版口径都被实测作废
  （绝对值永远为真；差值被 md5 的 ≈600ms 与 ±100ms 噪声淹没）。最终对**残差**设预算：

  ```
  固定开销 = 首字节 − Worker 实测哈希 − 实测合并窗口
  ① 固定开销(48MB) − 固定开销(8MB) ≤ 100ms   ← P1-2 哨兵（基线 −5~14ms）
  ② 固定开销(1KB) ≤ 500ms                    ← 防固定开销总量劣化（基线 146~223ms）
  ```

  实现在 `e2e/first-byte.budget.spec.ts`，随常规 e2e 一起跑（12 条）。

**前端残留风险**：`authToken` prop 允许静态硬编码（README 已标注"不建议"），但没有运行时警告。
建议开发环境检测到 `authToken` 非空且未传 `getAuthToken` 时 `console.warn` 一次。

### 5.2 后端（这部分完成度高于多数参考实现）

- **路径安全**：`sanitizeFileId` / `sanitizeFilename` / `isValidMd5` / `resolveInsideBase` 全链路；
  合并前对 staging 与分片路径都做 `inspectWriteTarget`（`lstat` 拒绝非普通文件）+ `O_NOFOLLOW` 写，
  堵住符号链接 TOCTOU（VU-34）。
- **越权**：`user_id` 由鉴权中间件派生（`buildPrincipalId` = sha256(token) 前 32 位），
  请求体里的 `user_id` 一律忽略；秒传查询、分片查询、落库键全部叠加 `user_id`（P2-9）。
- **鉴权默认 fail-closed**：`createAuthMiddleware` 未拿到有效凭据一律 401；Cookie 分支**必须**命中白名单，
  不做"存在即通过"（P0-3）；`safeTokenEqual` 用 `timingSafeEqual` 且先比长度。
- **DoS**：单文件 / 全局 / 用户三维容量 + 分片数封顶；JSON body 上限 8MB 且 parser 顺序在鉴权之后；
  `chunk_md5s` 逐元素校验（长度 ≤ 64、无空白）；合并锁有等待超时与等待者上限。
- **崩溃一致性**：先写盘 → `enqueueChunkState` → `flushFileChunkStates` 后才回 200（消除"盘上有、库里没有"窗口）；
  合并失败只清 staging，源分片保留供续传（VU-59）。
- **信息泄露**：4xx 保留原文便于定位，5xx 统一 `redactErrorMessage`（去掉 SQL、绝对路径）。

### 5.3 残留风险（运维层，非代码缺陷）

1. **Cookie 鉴权无 CSRF 防护** —— 项目已自我标注（VU-21）为部署方责任。若真用 Cookie 模式，
   需网关层加 `SameSite=Lax/Strict` 或 CSRF token。
2. **`/auth` 之外的接口无速率限制以外的滥用防护** —— 秒传查询可被用来枚举"某 md5 是否已被本用户上传"，
   影响有限（同用户维度），可接受。
3. **`Dockerfile` 与 `.env.example`** 未在本次通读范围内逐行审；部署前建议核对 `AUTH_MODE` 默认值与卷权限。

### 7.6 状态转换矩阵

| 当前状态 | 事件 | 条件 | 动作 | 目标状态 |
|---|---|---|---|---|
| QUEUED | 批次取走 | 在线 & 记录存在 | 写 PREPARING_UPLOAD + `syncFile` | PREPARING_UPLOAD |
| PREPARING_UPLOAD | 缓存就绪 | `prime` 或 `isFileCacheReady` | 提交 Worker 任务 | UPLOADING |
| PREPARING_UPLOAD | 缓存缺失 | 无 fileRef 且无缓存 | 写 ERROR + `awaitingReselect` | ERROR |
| UPLOADING | Worker 完成 | `/merge` 200 | progress=100，释放 fileRef，清缓存 | DONE |
| UPLOADING | 秒传命中 | 预检 `uploaded:true` | 清缓存 | INSTANT |
| UPLOADING | 用户暂停 | 状态=UPLOADING | 分片边界挂起；速率/ETA 归零 | PAUSED |
| UPLOADING | 用户取消 | 状态=UPLOADING | abort + 标记 userCancelled | PAUSED（保留进度） |
| UPLOADING | 批次取消 | 批次 abort | 乐观落定 PAUSED，bridge 800ms 兜底结算 | PAUSED |
| UPLOADING | 终态失败 | 重试耗尽 | 清缓存 + `onUploadError` | ERROR |
| PAUSED | 用户继续 | Worker 存活 | `resume` 消息 | UPLOADING |
| PAUSED | 用户继续 | Worker 已释放但缓存就绪 | 重新发起上传（服务端 /status 续传） | UPLOADING |
| PAUSED | 用户继续 | 无缓存 | 提示重选 | ERROR |
| ERROR | 用户重试 | 在线 | 写 PREPARING_UPLOAD | PREPARING_UPLOAD |
| 任意 | 用户删除 | 任意状态 | abort Worker + 清两端 | （移除） |
| DONE/INSTANT | 倒计时归零 | `autoCleanup` | 从 IDB/store/缓存移除 | （移除） |
| DONE/INSTANT | 倒计时期间变在途 | BR-09 | 移出待清理集合 | 保持原状态 |

**非法转换（必须无路径）**：`QUEUED → DONE`（跨过上传）、`ERROR → DONE`（跳过重试）、
`PAUSED → DONE`（跳过继续）、`任意 → UPLOADING`（未经 PREPARING_UPLOAD）。
